# 0021 厨房「可做」匹配的保守语义

- 状态：已实施
- 日期：2026-11-12

## 背景与依据

「可做」是根据厨房库存判断已记录的需求是否满足，不等同于「推荐中出现」。现有数据的多厨具没有「替代组 / 同时需要」字段：

- [数据准则](../dev/data.md) 将 `tools` 称为必要厨具，要求根据来源实际操作填写；顿号只表示多个值，未定义为任选其一。
- [CSV](../../packages/data/recipe.csv) 中 id 881、882、886 同时记录「一口大锅、烤箱」，id 884 记录「一口大锅、料理机」。[机构审核记录](../../packages/data/recipe-institutional-low-gi.json) 对 881 明确要求可上灶、可入烤箱的有盖锅，并记录先炒煮再入烤箱；882 先煎茄子、炒蔬菜后进烤箱；884 大锅煮软后料理机打碎。这些是组合，不是替代。
- 旧数据如 id 91「欧洲家庭版欧包」的「烤箱、电饭煲」、id 595–597 的「一口大锅、电饭煲」也可能混有替代做法。仅凭列表和菜名无法可靠区分，不据此给全库默认 OR，也不声称已经逐菜核验旧视频。
- [推荐实现](../../packages/cook/src/utils/recommend.ts) 的单厨具筛选使用 `recipe.tools.includes(tool)`。这是发现候选的入口，不验证其他厨具齐全，不能作为「已具备全部条件」的依据。

## 决定

共享纯函数 `canCookWithKitchen(recipe, kitchen)` 接收 `stuff` / `tools` 和 `{ ingredients, pantry, tools, initialized }`，不读取 store 或持久化：

1. 厨房尚未初始化时返回 `false`。
2. 通过现有 `uniqueStuff` 对菜谱及库存食材进行别名、分隔符、空白、去重处理。食材来源为显式 `ingredients ∪ pantry`，绝不默认拥有任何调料，也不从菜名推断必需材料。
3. `stuff` 中记录的食材必须全部满足，包括发现推荐中作为大杂烩候选的菜谱；「可做」不沿用宽松推荐或大杂烩的缺料豁免。
4. 多厨具按 **AND 组合** 判断，必须全部拥有；厨具仅处理分隔符、首尾空白和重复值，不将食材别名套用到厨具，不推断锅具可互相替代。
5. `stuff` 或 `tools` 缺失、空数组、或标准化后为空均表示信息不足，返回 `false`，不利用空集合的全称判断自动认定可做。

## 影响与局限

- 不改现有推荐排序、筛选、CSV 或厨房存储结构。列表与详情应调用同一纯函数，以免出现不同结论。
- 混有替代厨具的旧条目可能产生保守的假阴性，但不会因只拥有组合中的一种而误标可做。需要支持替代时，先逐菜核验并增加显式替代组数据结构与对应校验，再改变匹配规则，不按菜名猜测。
- 返回 `true` 仅说明数据已记录的要求满足；公共 CSV 通常不列常备调味料，不能声称已核实教程的全部配方或实际库存数量。若 `stuff` 明确列出了某种调料，就必须在用户库存中明确存在。
