# 0026 用户投稿发布到全量菜谱

- 状态：已采纳
- 日期：2026-11-27
- 关联：[0023 官方菜谱覆盖层](./0023-recipe-overrides)、[0013 私人菜谱](./0013-private-recipes)、[0025 我的菜谱云同步](./0025-custom-recipe-cloud-sync)

## 背景

「我的菜谱」是个人副本，别人看不到；「全量菜谱」的运行时补丁层虽然能改已有菜谱，但**只能改，不能新增**——客户端的合并按本地数据集逐条查覆盖，不在里面的 id 会被静默丢掉。所以用户抄到的好菜谱没有任何通路进入收录库。

需求有两条：

1. 自己加的菜可以投稿，管理员审核后对所有用户可见；
2. 新增或修改过的菜谱，在「我的菜谱」和「全量菜谱」两边都能快速找到。

## 方案对比

| 方案                           | 取舍                                             |
| ------------------------------ | ------------------------------------------------ |
| 站内即时发布，登录即可写       | 最快，但没有审核，任何人都能往全站塞内容         |
| **投稿 → 审核 → 发布**（采纳） | 有把关，代价是多一张表和一页审核界面             |
| 只导出补丁 CSV，人工合回仓库   | 零风险，但发布周期是「下次构建」，不适合日常使用 |
| 重做数据服务与在线编辑后台     | 对个人站点过重                                   |

## 决定

- **投稿**：任何登录用户都能提交自己的一道路菜；管理员在「投稿审核」里看到「提交什么 / 会发布什么」的对照，通过后立刻对所有访客生效。
- **发布即写入覆盖层**：审核通过时服务端分配新 id，写入 `recipe_overrides`（`source = 'submission'`）。公开读接口零改动，客户端合并改成补丁驱动后就能看到。
- **客户端合并改为补丁驱动**：`applyRecipeOverrides` 除了按 id 打补丁，还会**追加本地数据集里没有的补丁**。这是「新增菜谱能触达用户」的关键改动——以前只做替换，发布出去的菜谱永远看不到。
- **id 分配**：新增环境变量 `COOK_PUBLISHED_ID_BASE`（默认 10000）。发布的 id 从高位预留段分配，与官方数据集的 id 段（当前 0..887）不相交，将来补丁 CSV 回灌 `recipe.csv` 也不会撞号。
- **计数器是唯一真相**：`counters` 表单调递增。不能只靠 `MAX(recipe_id)`——删掉一条已发布的记录会把 id 重新发出去，违反「id 一经发布就固定，永不复用」。id 在**审核通过时**才烧掉，被驳回的投稿不占号。
- **步骤正文放进 `note`**：覆盖层白名单增加 `note`，`RecipeItem` 增加可选 `note`，详情页的步骤改成三段——有 `recipe-text.json` 用它，否则有 `note` 就渲染 `note`。
- **投稿时剔除词典外食材**：官方食材必须在 `packages/data/food.json`（87 项）里，葱姜蒜、油盐酱醋不在（它们在常备调料里单独计算）。投稿前自动剔除并告诉用户剔了哪些，否则补丁 CSV 合回 `recipe.csv` 时过不了 `pnpm validate`。厨具同理。剔完一样食材不剩则不允许投稿。
- **个人副本保留**：发布后「我的菜谱」里那一份仍在（用户明确要求两边都有）。
- **两边互见**：
  - 「我的菜谱」页面新增「我修改过的官方菜谱」一段（仅管理员可见），数据来自 `GET /api/recipes/overrides/mine`；
  - 「全量菜谱」页面新增「官方菜谱 / 我的菜谱」分段，后者列出自己的私人菜谱与投稿状态。
- **补丁 CSV 排除发布菜谱**：CSV 没有 `note` 列，导出会把步骤丢掉，还会让 id ≥ 10000 的行混进 `recipe.csv`。

## 影响

- 新增环境变量 `COOK_PUBLISHED_ID_BASE`；`recipe_overrides` 新增 `source` 列，`recipe_submissions` / `counters` 两张新表。
- 发布菜谱没有 `recipe-text.json`、`recipe-amounts.json`，也没有饮食目标 / 次日午餐 / 机构低 GI 的审核条目：选了这些审核场景时它会被过滤掉。这是「尚未审核」的预期行为。
- 补丁层没有 `score`，发布菜谱按 `DEFAULT_RECIPE_SCORE` 参与排序；**浏览列表按基表顺序排，发布菜谱落在 887 道之后**（按关键词搜能找到）。这是发布体验里最弱的一环。
- 管理员删掉一条已发布的补丁，收藏过它的用户会静默失去这条收藏（收藏按 id 关联），投稿状态记为「已撤回」。
- `GET /api/recipes/overrides` 每次返回全部覆盖，发布菜谱会让它慢慢变大；个人站点量级可接受，后续可加 `since` 参数。
- 想让发布内容永久固化，仍走「导出补丁 CSV → 合回 `recipe.csv` → `pnpm convert` → `pnpm validate` → 提交」；`recipe.csv` 依旧是唯一权威源。
