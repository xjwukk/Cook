# 0024 料理助手：上传图片识菜谱

- 状态：已采纳
- 日期：2026-11-26
- 关联：[0021 料理助手](./0021-cooking-assistant)、[0018 冰箱拍照录入](./0018-fridge-photo-intake)、[自托管部署](../dev/self-hosting)

## 背景

「料理助手」只能吃文字。用户手里的菜谱大多是小红书 / 抖音的截图：一张「食材准备」表（姜蒜粒、葱花、鲜虾 500g），一张「做菜步骤」九宫格（油热平铺下锅、生抽 2 勺……）。截图里的中文就是菜谱本身，但用户只能一个字一个字抄进「添加菜谱」表单。

目标：助手能一次接收多张图片，读图后直接产出**可保存的菜谱草稿**，复用现有的草稿卡片 → `buildCustomRecipe` → `saveCustomRecipe` 链路。

## 方案对比

| 方案                           | 取舍                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| 纯本地 OCR（浏览器端识别中文） | 不依赖云端，但中文截图字体小、背景花，识别质量差，还要引入几 MB 的依赖 |
| 客户端 OCR + 文字模型          | 识别与生成分开两步，两次请求之间还要自己拼装上下文，步骤顺序容易错位   |
| **多模态模型直读（采纳）**     | 模型同时看图和写菜谱，顺序与上下文一次成型；代价是依赖模型支持图片     |
| 服务端存图再识别               | 与 0018「照片只在本机处理」的隐私基调冲突，还要引入对象存储与清理策略  |

## 决定

- **图片只作输入**：不落盘、不入库、不写进保存的菜谱，也不进账号同步。服务端只在内存里转发给模型服务商。
- **传输用 base64 JSON，不用 multipart**：服务端是零依赖 `node:http`，只有 JSON 解析器；为图片另写一套 multipart 解析不值得。客户端压缩后总体积 ≤ 3 MB，落在现有请求体上限内。
- **客户端压缩**：最长边 1280 像素、JPEG 质量 0.82，单张 ≤ 700 KB、单轮 ≤ 4 张、合计 ≤ 3 MB；超限时依次降质量、再缩小边长。支持文件选择、粘贴与拖拽三种入口。
- **服务端白名单校验**：只接受 JPG / PNG / WebP 的 base64（拒绝 svg、gif），校验张数、单张与总体积；归一后只保留 `{ mime, data }` 两个字段。
- **多模态请求**：最后一条 user 消息的 `content` 变成数组（`text` + `image_url`）。无图时仍是纯字符串，行为与旧版一致。
- **图片模型可选**：助手设置新增「图片模型」字段，与主模型共用 base URL 与 API Key；留空表示跟随主模型。上游明确拒绝图片时，服务端把状态码翻译成「当前模型不支持图片，请填写图片模型」的提示，而不是干巴巴的 502。
- **带图时候选池收紧到 10 条**，`max_tokens` 放宽到 3000：图片才是这一轮的重点。
- **只给草稿也算有效回复**：原先「没有 answer / picked / needs 就判非法」会让只回草稿的读图请求被拒，现在 `actions` 也计入有效内容。
- **食材必须是「现有菜谱菜单」里的**：客户端把 `food.json` + 常备调料 + 用户个人目录的食材名作为白名单随请求发送，模型不得自创；客户端再兜底归一（鲜虾→虾、葱花→葱、鸡翅→鸡肉）。对不上菜单的名字原样保留，不静默丢掉主料，并在草稿里提示。
- **用量写进步骤句**：菜谱模型没有用量与步骤字段，步骤与用量一起写进 `note`，格式与现有菜谱步骤一致（`1. …`、`2. …`），详情页按 `pre-wrap` 换行显示。
- **多图由模型自行分组**：同一道菜的「食材图」和「步骤图」合并成一份草稿，属于不同菜则各自出一份（带图时最多 6 份）。
- **看不清就标存疑**：模型在 `note` 里标「（存疑）」，并在 `warnings` 里写明哪张图无法辨认，不把猜测写进食材或步骤。

## 影响

- 新增环境变量 `COOK_AI_VISION_MODEL`、`COOK_AI_MAX_IMAGES`、`COOK_AI_MAX_IMAGE_BYTES`。
- `ai_config` 表新增 `vision_model` 列，旧库启动时自动补列（留空表示跟随主模型）。
- 新增分析事件 `attach_assistant_image`、`assistant_image_unreadable`，均不含图片内容与菜名。
- 图片会被转发给模型服务商用于识别，服务器不保存图片；分发给他人使用时，需要在隐私说明中告知这一点。
