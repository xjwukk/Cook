# 0025 我的菜谱参与账号云同步

- 状态：已采纳
- 日期：2026-11-27
- 关联：[0013 私人菜谱](./0013-private-recipes)、[0021 料理助手](./0021-cooking-assistant)

## 背景

「我的菜谱」一直只存在本机 `localStorage`（`cook:u<uid>:custom-recipes`）。换设备、换浏览器、清缓存，自己抄下来的菜就没了；而收藏、历史、我的厨房早就跟着账号同步。

0013 当时把「是否增加 Web 账号云同步」列为待定，理由是私人菜谱要用独立协议、不掺进收藏历史的 v1 文档。现在确认要做，这条待定项就此关闭。

## 方案对比

| 方案                               | 取舍                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 继续只存本机，靠导出/导入文件迁移  | 零改动，但换设备要手动搬文件，用户会丢数据                             |
| **并进现有的账号同步文档**（采纳） | 复用已有的合并、墓碑、防抖上传、旧客户端兼容；代价是文档变大，要加上限 |
| 单独一张表、单独接口               | 隔离干净，但要再写一套合并与冲突逻辑，且仍要和整份文档同步协同         |
| Dexie/IndexedDB 存私人菜谱         | 脱离 `useStorage` 体系，备份与导入导出全要重写                         |

## 决定

- **字段口径沿用私人菜谱协议**（`packages/cook/src/utils/custom-recipes.ts` 的 `PrivateRecipe`），不走 Web 内部的 `CustomRecipe`。后者继承 `RecipeItem`，带 `id/emojis/score`，这些键不在 `RECIPE_FIELDS` 白名单里。
- **合并规则**：按 `customId` 取 `updatedAt` 最大的一条；`updatedAt` 相同但内容不同时取规范写法字典序小的（保证可交换）；**同一时刻删除胜过写入**；写入严格晚于删除的，墓碑作废（重新加回来会复活）。墓碑沿用 180 天 TTL，上限 1000 条。
- **删除必须留墓碑**：`removeCustomRecipe` 除了过滤数组，还要往 `userDataMeta` 写一条墓碑，时间取 `max(now, 菜谱.updatedAt + 1)`，避免设备时钟慢时删不掉。没有墓碑的话，删掉的菜谱会从云端同步回来。
- **写回本机只做并集，不做替换**：切换账号时同步走 `data = remote.data`（不合并），整体替换会抹掉新账号本机的菜谱；体积裁剪后的文档也会误删。
- **体积上限**：客户端只同步最近 2000 道 / 2 MB 以内，超出部分留在本机并在「我的」页提示；服务端 4 MB 闸门，超了返回 413「私人菜谱超出同步上限」。
- **旧客户端兼容**：`PUT /api/user-data` 在 `customRecipes === undefined` 时回填服务端已存的那份。**判定必须是 `undefined` 而不是 falsy**——空数组表示「我全删了」，误判成旧客户端会让删除永远同步不上去。
- **投稿状态另存**：`cook:u<uid>:custom-recipe-publications`。绝不往 `custom-recipes` 里的菜谱对象上加字段——`validatePrivateRecipe` 遇到未知键会让整份数组读不出来。
- **`USER_DATA_VERSION` 保持 1**：升版本会让旧的「收藏与历史」导出文件再也导不进来。

## 影响

- 「收藏与历史」导出文件现在也包含私人菜谱，等于多了一条设备迁移通道。
- `readPrivateRecipeStorage` 会把整份数组交给 `validatePrivateRecipe`，所以同步写回的菜谱必须是干净的白名单字段。
- 文档体积随菜谱数量增长；个人量级下可接受，`GET /api/user-data` 仍是一次性整份返回。
