# 0023 官方菜谱的全局覆盖层

- 状态：已采纳
- 日期：2026-11-16
- 关联：[全量菜谱管理与官方菜谱修改](/dev/recipe-admin)

## 背景

官方菜谱在构建时从 `packages/data/recipe.csv` 打包进静态资源，运行时只读地存在浏览器 IndexedDB。写错了食材、视频失效或难度标错，只能改 CSV、重新构建、重新发布；管理员在站点内无法直接修正。

「我的菜谱」不能解决这个问题：它是另复制一份的个人副本，只保存在当前设备，既不会全局生效，也不参与官方数据的维护。

## 方案对比

| 方案                       | 结果                                        |
| -------------------------- | ------------------------------------------- |
| 把官方菜谱复制成个人菜谱   | 每人一份，改完别人看不到，也不回灌 CSV      |
| 让浏览器直接改 IndexedDB   | 只影响本机，构建产物无法回写，且冲突无解    |
| 服务端存覆盖层，运行时合并 | 全局生效，无需重新构建，可导出补丁 CSV 回灌 |
| 重做数据服务与在线编辑后台 | 对个人站点过重，还要处理权限、审核与并发    |

## 决定

服务端新增 `recipe_overrides` 表，按 `recipe.csv` 的固定 `id` 存整份 `RecipeItem` JSON。管理员通过「我的 → 全量菜谱」修改，公开接口 `/api/recipes/overrides` 免登录返回白名单字段，客户端在读取 IndexedDB 之后按 id 合并。浏览页不出现任何管理元素。

`recipe.csv` 仍是唯一权威源，覆盖层是运行时补丁：

- 管理员改完立即对所有访客生效，无需重新构建；
- 需要永久固化时，管理页导出补丁 CSV，合回 `recipe.csv`，`pnpm validate` 通过后提交，再删除覆盖记录；
- 撤销修改就是删除该行，回落到官方版本。

写入只允许管理员，服务端按形状校验字段（菜名、食材、厨具、做法、难度、视频号、图文链接），单条不超过 8 KB。冲突按 `updated_at` 后写胜出，个人站点不做多人合并。

## 影响

- 覆盖层只在内存中合并，不写回 IndexedDB，不改数据库 schema 版本；
- 推荐、搜索、菜谱库、收藏、历史、料理助手候选都读取合并后的结果；
- 文字步骤正文仍来自 HowToCook 并带指纹校验，不在本轮在线编辑范围内，避免审核数据失效（2026-11-27 起可通过 `note` 覆盖，见 [0027](./0027-official-recipe-step-editing)）；
- 收藏和历史仍按固定的 `id` 关联，菜名变化不会让收藏丢失。

## 2026-11-27 补充：步骤可以通过 note 在线覆盖

见 [0027 官方菜谱步骤在线编辑](./0027-official-recipe-step-editing)。管理员可以在「全量菜谱」编辑器里预览 `recipe-text.json` 的步骤，点「编辑步骤」后用 `note` 覆盖；清空则回退到官方正文。`recipe-text.json` 与指纹校验数据本身不改。
